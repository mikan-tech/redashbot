# RedashBotのGCE / Cloud Run費用比較と移行判断

作成日: 2026-08-13

## 結論

Playwrightのプロセスリークは、GCEのマシンスペックを上げても恒久的には解決しない。`capture()` の全例外経路でブラウザを終了する修正を、GCE継続・Cloud Run移行のどちらでも先に適用する。

`#kpi` の実投稿を2025年8月〜2026年7月で集計すると、RedashBotのキャプチャは合計3,731回、月間284〜357回（平均約311回）だった。Cloud Runを1 vCPU・2 GiB・30秒/回という保守的な条件で計算しても、現在の月間利用量はリクエストベースの無料枠内に収まる。無料枠を他サービスがすべて消費している場合でも、Cloud Runのランタイム費用は月約$0.25〜$0.31であり、GCEの計算資源だけで約$12.23/月を下回る。

したがって、現状の利用量に限れば費用面の結論はCloud Runが明確に有利であり、Cloud Runへの移行を推奨する。ただし、Slack Events APIの応答時間、コールドスタート、Playwrightイメージの互換性を確認してから移行する。今回の変更では移行実装までは行わない。

## 現行GCEの状況

過去の「Redash Bot 再起動」セッションと運用情報から、現行構成は次のとおり。

| 項目 | 内容 |
| --- | --- |
| VM | `redashbot` |
| プロジェクト | `mikan-develop` |
| ゾーン | `asia-northeast1-b` |
| マシンタイプ | `e2-small`（2 vCPU shared core / 2 GiB） |
| コンテナ上限 | `mem_limit: 700m`, `pids_limit: 200` |
| 起きた事象 | コンテナは起動中のまま、PID数が200に張り付き、再起動で復旧 |

マシンタイプは `e2-micro` から `e2-small` に変更済みだが、再起動が必要な事象は再発している。これはホストのメモリだけでなく、コンテナのPID上限とブラウザ終了漏れが関係するため、さらなるスペック増強は根本対策にならない。

GCP請求明細はこの環境から取得できなかったため、ディスク、外部IP、通信、税を含む実請求額は未確定とする。

## GCEの費用

東京リージョンのオンデマンド料金を使う。`e2-small` は `$0.016752855 / 時間` で、730時間/月とすると計算資源だけで次の金額になる。

```text
$0.016752855 × 730時間 = $12.23 / 月
```

実際のGCE月額は次の合計になる。

```text
VM計算資源 $12.23
+ Persistent Disk
+ 外部IP
+ ネットワーク転送
+ その他のGCP利用料・税
```

参考: [Compute Engine VM料金](https://cloud.google.com/products/compute/pricing/general-purpose)、[E2マシンタイプ](https://docs.cloud.google.com/compute/docs/general-purpose-machines)

## Cloud Runの試算

RedashBotはHTTPのSlack Events APIを受けるため、Cloud Run Serviceとして試算する。以下を基準シナリオとする。

| 項目 | 試算値 |
| --- | --- |
| リージョン | `asia-northeast1`（東京、Tier 1） |
| 課金 | リクエストベース |
| 最小インスタンス | 0 |
| CPU | 1 vCPU |
| メモリ | 2 GiB |
| 同時実行数 | 1 |
| 1キャプチャの処理時間 | 30秒（保守的な試算値。代表日のSlack投稿では約5〜6秒） |

現在の公式単価は、アクティブなリクエスト処理でCPU `$0.000024 / vCPU秒`、メモリ `$0.0000025 / GiB秒`、リクエスト `$0.40 / 100万リクエスト`。リクエストベースの無料枠は、請求アカウント単位でCPU 180,000 vCPU秒、メモリ360,000 GiB秒、リクエスト200万/月。

30秒/件、1 vCPU、2 GiB、無料枠をこのサービスが利用できる前提でのランタイム費用は次のとおり。

| 月間キャプチャ数 | CPU使用量 | メモリ使用量 | Cloud Runランタイム概算 |
| ---: | ---: | ---: | ---: |
| 1,000 | 30,000 vCPU秒 | 60,000 GiB秒 | $0.00 |
| 5,000 | 150,000 vCPU秒 | 300,000 GiB秒 | $0.00 |
| 10,000 | 300,000 vCPU秒 | 600,000 GiB秒 | $3.48 |
| 20,000 | 600,000 vCPU秒 | 1,200,000 GiB秒 | $12.18 |
| 50,000 | 1,500,000 vCPU秒 | 3,000,000 GiB秒 | $38.28 |

### 実績利用量での試算

30秒/件、1 vCPU、2 GiB、リクエストベースの単価で計算すると、1キャプチャあたりのランタイム費用は無料枠適用前で約`$0.0008704`となる。12か月実績の月間キャプチャ数では、CPU使用量は最大10,710 vCPU秒、メモリ使用量は最大21,420 GiB秒であり、Cloud Runの無料枠（CPU 180,000 vCPU秒、メモリ360,000 GiB秒、リクエスト200万/月）を大きく下回る。

| 利用量 | CPU使用量 | メモリ使用量 | 無料枠が残っている場合 | 無料枠をすべて他サービスが消費した場合 |
| --- | ---: | ---: | ---: | ---: |
| 実績平均 約311件/月 | 約9,328 vCPU秒 | 約18,655 GiB秒 | $0.00/月 | 約$0.27/月 |
| 実績最小 284件/月 | 8,520 vCPU秒 | 17,040 GiB秒 | $0.00/月 | 約$0.25/月 |
| 実績最大 357件/月 | 10,710 vCPU秒 | 21,420 GiB秒 | $0.00/月 | 約$0.31/月 |
| 12か月実績合計 3,731件 | 111,930 vCPU秒 | 223,860 GiB秒 | — | 約$3.25/年相当 |

無料枠をRedashBotだけで使う場合、30秒/件では月6,000件程度まで無料枠内となる。無料枠を考慮しない損益分岐点は約14,000件/月であり、RedashBotだけで無料枠を使う前提では約20,000件/月となる。実績平均の約311件/月は、後者の損益分岐点の約1/64である。ディスク・IP・通信を含めたGCE実請求額は計算資源費用より高くなるため、実額ベースではCloud Run有利の差はさらに広がる。

無料枠を他サービスが使い切っている場合、同じ基準シナリオのCloud Run費用は10,000件で約`$8.70`、20,000件で約`$17.40`、50,000件で約`$43.50`となる。請求アカウント全体の無料枠使用量を確認する必要がある。

Cloud Runの請求は100ミリ秒単位で丸められ、最小インスタンス0の場合、アイドル中のインスタンスには課金されない。Artifact Registryのイメージ保管、Cloud Build、外向き通信、ログなどは別料金である。

周辺費用についても、今回の利用規模では大きな追加費用は想定しにくい。Artifact Registryは請求アカウント単位でストレージ0.5 GiB-monthまで無料で、Cloud Runと同じロケーション間のデータ転送は無料である。Cloud Buildは請求アカウント単位で月2,500ビルド分まで無料（既定の`e2-standard-2`プールの場合）で、超過時は`$0.006 / ビルド分`が目安となる。実際のイメージ保持量、ビルド回数、請求アカウント全体の無料枠消費量、外向き通信量、ログ量は未確認のため、最終的には請求明細で確認する。

参考: [Cloud Run料金](https://cloud.google.com/run/pricing)、[Artifact Registry料金](https://cloud.google.com/artifact-registry/pricing)、[Cloud Build料金](https://cloud.google.com/build/pricing)

## 運用面の比較

| 観点 | GCE | Cloud Run |
| --- | --- | --- |
| 常時稼働費 | e2-smallの固定費が発生 | 最小インスタンス0ならリクエスト時中心 |
| プロセスリーク | 同一コンテナが長期間残り、PID上限に到達し得る | インスタンス単位で分離されるが、再利用中のリークは残る |
| 障害復旧 | VM/コンテナの監視・再起動が必要 | インスタンス再作成はマネージドだが、アプリの終了処理は必要 |
| コールドスタート | 基本なし | Playwright起動時間がSlack応答に影響し得る |
| Slackリトライ | 現行運用を継続 | 3秒以内の応答と重複イベントを検証する必要がある |
| デプロイ | VM上のDocker運用 | Artifact Registry経由のイメージデプロイ |

Cloud Runへ移行する場合も、`PORT`環境変数で待ち受けるHTTP Serviceとして構成し、`min-instances=0`、同時実行数1、適切な最大インスタンス数を設定する。Cloud Runは終了時にSIGTERMを送るため、ブラウザや子プロセスを確実に終了できる設計を維持する。

Playwrightは現行の`1.46.1`と`mcr.microsoft.com/playwright:v1.46.1-focal`を維持し、移行のためだけにイメージを更新しない。互換性検証なしのバージョンアップは、過去に発生したスレッド生成失敗を再発させる可能性がある。

## 判断

現時点では、次の順序を推奨する。

1. `capture()`の`finally`によるブラウザ終了保証をリリースする
2. `#kpi`の12か月実績（284〜357件/月、平均約311件）を費用比較の基準として使う
3. Cloud Runで同じPlaywrightイメージを使った検証環境を作り、Slackの検証イベント・実イベント・リトライ・SIGTERMを確認する
4. 検証が通れば、今回の利用量ではCloud Runが明確に安い前提で移行する。移行前にGCEの実請求額とCloud Runの請求アカウント全体の無料枠消費を最終確認する
5. 移行後に一定期間安定稼働を確認してからGCEを停止する

費用と運用負荷の両面ではCloud Run移行を推奨する。ただし、Playwrightの終了漏れ修正は移行の前提条件であり、Cloud Runへ移すだけでは恒久対策にならない。
